## 一、这一轮解决的核心矛盾

F3 结束时系统有两套不一致的行为：

| 路径 | 用户说「不要 Rothy's」之后 |
| --- | --- |
| 换件 | 候选池里 Rothy's 全部消失（硬排除） |
| 新建方案 | 模型仍可挑一件 Rothy's，方案**照样存进去**，只在回复里附一句"存在偏好冲突" |

这不是提示词问题，是**两条路径用了不同的约束层**：换件走 `rankCandidatesDetailed`（硬过滤在 pool 阶段），建方案走 `createPlan`（先落库、再检查）。

F4 把建方案拉到同一条铁律上：**先校验、后落库；不确定就不放行**。

## 二、A1：统一硬约束

### 2.1 新增的校验层（纯函数，可单测）

`packages/core/src/ranking.ts`

```ts
validatePlanAgainstPrefs(plan, prefs, ctx, { allowRules })
  → { violations, exempt, applied, unmapped, checks }
```

- `violations`：命中 `prefExclusionHits` 的商品（尺码 / 避开品牌 / 避开词），**非空即拒绝**
- `exempt`：被用户本轮明确授权破例的冲突（仍展示，便于复核）
- `applied` / `unmapped`：照抄 F2 的口径 —— 认不出的自由文本进 `unmapped`，**不冒充已校验**
- `checks`：预算 / 到货 / 收货地 / 自由文本四项，三态 `ok | violated | unverified`

三条三态纪律（防止「没检查」被说成「检查通过」）：

1. 关税 `unavailable` 时总额本身不是确认值 → 预算只能 `unverified`，不能 `ok`
2. `arrival.verdict = unknown`（缺时效）→ `unverified`；`at_risk` → `unverified`（有延误风险）
3. 收货地不等于 `CN` 时没有对应运费/时效规则 → `unverified`，不假设"全球都能送"

### 2.2 建方案改为「内存校验 → 通过才落库」

`packages/bridge/src/state.mjs#createPlan`

```
校验 slots / 类目 → 建内存方案（含成本与到货）→ validatePlanAgainstPrefs
  → 有 violations：抛 PREF_CONFLICT（不 set、不 persist、不广播）
  → 只有明确破例：写 plan.constraints.prefExceptions → 落库
```

错误结构（HTTP 422）：

```json
{
  "code": "PREF_CONFLICT",
  "error": "这套方案有 1 件商品与你已确认的偏好冲突：鞋「The Point III」—— 你要求避开 Rothy's",
  "hint": "可以：① 换掉冲突商品后重新提交；② 到首页修改或删除对应偏好；③ …",
  "details": {
    "violations": [{ "slot": "shoes", "productId": "...", "title": "...", "reasons": ["你要求避开 Rothy's"], "rules": ["brand_avoid"] }],
    "actions": [
      { "action": "replace_items", "label": "换掉冲突商品" },
      { "action": "edit_prefs", "label": "修改 / 删除对应偏好" },
      { "action": "allow_once", "label": "用户明确授权本方案破例", "rules": ["brand_avoid"] }
    ]
  }
}
```

### 2.3 「破例」为什么记在方案上，而不是改偏好

用户说"这次破例"不等于"以后都不介意"。所以：

- 授权只写进 `plan.constraints.prefExceptions = [{ rule, quote, at }]`（含用户原话）
- **长期偏好一个字都不改** —— 实测：破例建完方案后，换件候选里 Rothy's 仍然被排除
- 校验器只认 `brand_avoid / avoid / size_top / size_bottom / size_shoes` 五个真实规则 ID；
  模型编一个规则名不能放开任何东西；缺用户原话（<4 字）直接拒绝

### 2.4 顺带补上的类目校验

`createPlan` 现在校验 `item.category === slot`（409 `CATEGORY_MISMATCH`）。此前把"包"塞进"鞋"位会静默成功，
金额、到货、场景热点全部错位且没人会发现。

### 2.5 向后兼容

| 旧调用 | 现状 |
| --- | --- |
| `POST /api/plans` 不带 `prefOverride` | 行为不变（无偏好时完全一致） |
| 响应 `prefConflicts` | 保留（成功时为空数组） |
| `GET /api/plans/:id` | 只新增字段（`prefChecks/prefExempt/prefExceptions/prefConflicts`） |
| 旧方案（无 `prefExceptions`） | 读取正常，`planValidation` 按空处理 |
| `crosscart_create_plan` 旧参数 | 不变；新增两个可选参数 |

## 三、A2：排序行为没有被动过

- 权重未改：策略 0.40 / 到货 0.25 / 价格 0.20 / 风格 0.15 / 偏好加分 ≤0.10
- 硬排除仍在 pool 阶段，**被排除的商品不可能靠加分回来**（`rankCandidatesDetailed` 未改）
- `changedSlots === 1` 守卫未改（`applySwap` 未改）
- `cheaper` 双闸未改
- 无偏好时 `prefBonus = 0`，候选 ID/分数/顺序与 F3 基线逐位相同（`check:f2` 15/15、`verify` 46/46）

本轮唯一新增的计算是 `explainPick()`：为了解释"加分但名次没变"，它会用**同一套方案、同一策略、无偏好**再排一次，
只读不写。成本是每槽位一次内存排序（<1ms），不影响任何结果。

## 四、A3：解释链路（从计算到界面到 AI 回复）

### 4.1 数据链

| 层 | 字段 |
| --- | --- |
| 匹配/排序 | `prefBonus`、`prefWhys`、`excluded[].reasons`、`applied`、`relaxed`、`blockedBy`、`unmapped` |
| 换件响应 | `prefRanking.picked = { prefBonus, prefWhys, rankWithPrefs, rankWithoutPrefs, rankChanged, specified }` |
| 建方案响应 | `prefConflicts`、`prefExempt`、`prefApplied`、`prefUnmapped`、`prefChecks`、`prefExceptions` |
| 方案详情 | 同上（每次读取实时重算，偏好后来改了也会显示新冲突） |
| Studio | 候选抽屉 `偏好参与排序 / 已排除 / 无法匹配`；`#risks` 追加破例与冲突两条 |
| AI 回复 | 换件工具返回「偏好说明：加分多少、名次几→几 / 主要由策略价格到货决定」；建方案工具返回约束核查 |

### 4.2 三种说法严格分开

| 实际情况 | 系统怎么说 |
| --- | --- |
| 偏好被读取但候选中没有可匹配商品 | 「偏好参与了排序（…），但这件本身没有获得加分」 |
| 获得加分且名次前移 | 「偏好确实改变了名次：颜色符合…+0.05；无偏好时第 5，现在第 3」 |
| 获得加分但名次不变 | 「偏好给这件加了 0.05，但名次没有变化（第 3）—— 结果主要由策略、价格与到货决定」 |
| 没有任何生效偏好 | 「这次没有生效的偏好，结果与无偏好时一致」 |

实测证据：F3 里 `dark` 确认后确实生效（`applied` 从 light 切到 dark、3 件 +0.05），但鞋类基础分差 >0.05，
top3 没变 —— 现在系统会明确说"加分但名次未变"，不会再被理解成"因为偏好成了首选"。

## 五、A4：真实对话验证（真实 DeepSeek，12/12）

脚本：`npm run check:f4:dialog`（隔离目录 + 独立端口 8795 + 独立 `CROSSCART_BRIDGE_URL`）
证据：`docs/F4-对话验收.json`

| 场景 | 用户原话 | 模型工具调用 | 结果 |
| --- | --- | --- | --- |
| 明确长期偏好 | 「我以后都不喜欢荧光色，帮我记住。」 | `save_pref` + `list_prefs` | 写入 `avoid=荧光色（neon / 高饱和亮色）`，`source=ai`，带原话；**没有**覆盖已确认的 `palette=light` |
| 临时换件 | 「这次帮我换一件深色外套。」 | `list_catalog` → `plan_state` → `swap_item` | 换件成功；长期偏好前后逐字相同（`palette=light / avoid=…`），没有自动生成长期偏好 |
| 改主意 | 「我以前喜欢浅色，但现在更喜欢深色，以后按深色来。」 | `save_pref` + `list_prefs` | `palette=dark` 生效，`light` 标 `supersededBy`，brief 只剩 dark |

唯一"不完美"的地方也如实记录：场景一的模型回复说"以后选品都会过滤掉这一类"。
`avoid` 是字符串级匹配，中文词遇到英文标题可能命中 0 件 —— 已经在 `save_pref` 返回文案里加了明确限制说明，
避免模型把"记下来了"说成"一定能筛掉"。

## 八、遗留（不阻塞 F4 验收）

1. **AI 主动发现偏好仍靠模型自觉**：没有批量挖掘历史行为，F3 结论不变。
2. **自由文本偏好受商品标签限制**：中文避开词命中英文标题仍为 0；需要给商品补中文关键词，而不是调权重。
3. **预算不阻断建方案**：本轮按"用户自己的数字应可见而不是被隐藏"处理 —— 返回 `violated` 并进入 AI 回复与风险列表。
   是否要硬阻断，建议等真实使用反馈再定。
4. **破例授权依赖用户原话**：代码能校验"有没有原话"，不能校验"这句话是不是真的说过"；所以 UI 会展示原话供复核。
5. **单机共享状态**：F4.5 的演示环境是所有访问者共享一份数据，见部署文档的安全边界。

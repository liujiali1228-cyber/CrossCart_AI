### P9-1 具体做了什么

- **状态模型**：`Slot.ownedClaim` 从「只有 productId」扩成两种形态 —— 商品型（`{quote, at}`）和**抽象型**（`{quote, at, label, color}`）。抽象型允许 `item: null`，因为用户说「我有白色的鞋子」时系统里确实没有这件商品，**不能编一个商品来代替**。
- **建方案校验**（`state.mjs`）：抽象「已有」必须在**当前这段对话**里被用户提起过，否则 422 `OWNED_UNDECLARED`。判定方式是 `mentionsSlot()` 按槽位关键词（外套/大衣/鞋/靴/包…）去匹配 `chatEpochStart` 之后的用户消息；换新对话后旧声明自动失效。
- **提示词**（`scenes.ts`）：自有单品作为**独立硬约束**进入提示词，而不是混在衣服列表里：
  ```
  wearing cream wool coat jacket, white shoes, brown bag,
  the wearer's own white shoes and brown bag — these are the user's own items and must appear exactly as described,
  do not substitute any of them: the shoes must stay white shoes; the bag must stay brown bag, no other shoes or bag
  ```
- **缓存键**：`sceneCacheKey()` 把自有单品的 `slot:label:color` 也纳入哈希 —— 用户把「白鞋」改成「黑靴」，键必须变，否则会继续显示旧图。
- **上下文**（`plan-context.mjs`）：模型能看到「白鞋（用户自己的东西，系统里没有具体商品/链接，不要编一款商品代替，也不要在图里换掉）」；用户说「鞋子也重新帮我挑」时把该槽位改回 `to_buy`。
- **结果校验**（`hotspots.mjs` + `scenegen.mjs`）：生成后用像素亮度检查各槽位区域 —— 说浅色（白鞋）要求该区域 p90 ≥ 0.55，说深色（棕包）要求 p50 ≤ 0.72，落在中间地带记 `unclear`（不硬判，不为了交差乱扣）。判定为错时**只补画一次**（还须过预算闸门），并把 `ownedCheck` 结果挂到图上，界面如实提示「图里的鞋和你说的颜色对不上，可以再生成一次」。
- **界面**：右侧清单显示「自有 / 不计入」，商品图版位显示「自有 + 名称」，报价与预算都把它排除在外。

### P9-2 具体做了什么

后端本来就会在 `sceneAuto.enabled` 时自动排生成；重复确认来自前端：陈旧态的「更新穿搭图」按钮走 `regenerateScene()` → 未带 `confirm` → 弹确认框。现在：

- 自动模式开着时点「更新」直接提交（`{confirm:true}`），不再有第二个弹窗；
- 换件后舞台只显示一行「正在更新穿搭图…」，完成后原地换图；
- 自动模式关着时只更新清单/价格，图保持上一版并**明确标 stale**，不让旧图冒充当前搭配；
- 乱序保护：POST 响应和 SSE 事件都带 `cacheKey`，键和当前不一致就丢弃（重新拉一次方案），旧图不会盖新图；
- 连续换件靠防抖窗口合并（默认 1600ms，验收实例 1200ms），三次换件只生成一次。

### P9-3 具体做了什么

- 链接来源查清了：**不是模型编的，是工具返回值里带的** —— `planText()` 里有一行「可视化方案：${studioUrl}」，模型照抄。已从工具输出里删掉（结构化的 `studioUrl` 字段仍在，供页面用），并在对话规则里明确禁止写链接/方案编号；显示层再加一道 `cleanReply()` 兜底（清 markdown 链接、裸链接、`pln_xxx`、只剩空标签的「方案：」行，金额不动）。
- 分享能力没丢：顶栏新增「分享」按钮，复制当前地址。
- 说话方式：重写了 `plan-context.mjs` 的回复规则 —— 先讲为什么适合这个场景，再说花了多少（标明估算），不确定的到货/税费如实说；禁止「槽位/链路/已拥有状态/页面空位/执行完成」这类内部词；不套三段式模板。

## 二、根因分析：为什么旧版本画出了黑短靴

不是「提示词写得不够狠」，是三处叠加的结构性缺口：

1. **提示词只遍历有商品的槽位**（直接原因）
   `buildScenePrompt()` 用 `plan.slots.filter(s => s.item)` 拼穿搭描述。用户口头声明的「白鞋」没有 productId、`item === null`，于是**整条信息在拼提示词时被过滤掉了**。提示词里根本没有脚上穿什么，模型只能自由发挥 —— 画成黑短靴完全合理。

2. **模型自己也不知道**
   `plan-context.mjs` 同样用 `s.item` 过滤 `owned` 槽位。所以模型一边在回复里说「白鞋配得挺好」，一边在它看到的方案结构里那双鞋是不存在的。说的和画的来自两份不同的（都不完整的）事实。

3. **缓存键不含口头声明**
   `sceneCacheKey()` 只哈希有 productId 的槽位。用户把「白鞋」改成「黑靴」，键不变 → 命中旧图 → 界面继续显示上一张。也就是说即使前两条修好了，改口也不会更新。

附带问题：P6 的「已有必须是用户说的」只校验有 productId 的商品；抽象「已有」当时没有建模，所以「已拥有」可以来自历史方案或模型自己的推断。

**修复后的验证**（真实模型 + 真实生图，不是断言提示词里有没有 "white shoes"）：
`check:p9:dialog` 走真实对话 → 建方案 → 真实出图 → 取图检查。
`shots/p9/nyc-owned-white-shoes-brown-bag.png` 里是**白色运动鞋 + 棕色绒面包**，像素检查 鞋区 p90 = 0.745（浅色通过）、包区 p50 = 0.368（深色通过），`ownedCheck.ok = true`。

### 真实生图验证（不是「提示词里有 white shoes」）

- 输入：「我打算去纽约玩一天…预算 300 美元，我有白色的鞋子和棕色的包包，其它的你看着搭配。」
- 结构化结果：`shoes.status = owned`、`bag.status = owned`，`label` 分别是白色运动鞋/棕色包，`from` 指向那句用户原话；`to_buy` 里**没有**重复的鞋或包。
- 产物：`shots/p9/nyc-owned-white-shoes-brown-bag.png`（2.8MB 原图）+ `.webp`（164KB 页面图）。
- 像素判定：`ownedCheck = { ok: true, method: 'pixel-luma', checks: [鞋 p90 0.745, 包 p50 0.368] }`。
- 回复：口语、无链接、无编号 —— 「…新买的衣服大概 $222 左右（估算），预算 $300，还留着七八十块余量…」。

### 修掉的 4 个真 bug（都是这轮实测发现的，不是构造的）

1. 自动更新**状态机死锁**：防抖窗口比换件间隔短时，`finally` 只排下一轮不清 `running` → 新窗口又看到 `running=true` → 永远「正在更新」，一张图都出不来。
2. 合并补排用**过期方案快照**：补排按旧缓存键算 → 命中缓存直接返回 → 最新搭配永远没图（`status=missing`）。
3. 聊天区 `scroll-behavior: smooth` 导致最后一条回复被裁 10px。
4. 首页 `hero-mobile` 改成 WebP 后 `check:home` 的旧断言失败（断言跟着素材改，不是改素材迁就断言）。

### 已验证「换机器也能跑」

在本机用**全新 `DSH_HOME` + 只通过环境变量注入密钥**起了一个实例（`CROSSCART_PORT=8798`）：dsh 自动从模板初始化 profile、`provision-dsh-credentials.mjs` 只写一次凭据文件，随后真实模型正常回话。这一步等价于容器冷启动，是这条部署路线能不能成立的关键验证。

**未验证项**：本机没有 Docker，`deploy/Dockerfile` 没有真的 `docker build` 过。上面的冷启动验证是在 Windows 上原生跑的等价路径；镜像本身仍需平台首次构建时确认（这是遗留问题之一）。

## 七、遗留问题

1. **长期地址需要你授权一次**（见上）。在此之前，只有临时隧道地址可用，重启即变。
2. **镜像未在本机构建**（无 Docker）。Dockerfile 的逻辑依据是「全新 DSH_HOME 冷启动 + 环境变量注入密钥」的原生实测，但 `docker build` 本身没跑过。
3. **多人共享同一实例**：没有账号体系，所有人共用一套 `data-public/`。A 访客的偏好/方案会出现在 B 的页面里（演示可以，多用户不行）。真要多人用需要加登录与按用户隔离数据。
4. **抽象自有单品的判定是「量级级」的**：像素亮度只能发现「说白鞋、那块整体是深色」这类矛盾，判不了「那到底是不是鞋」。更细的识别需要视觉模型（`resolveVisionConfig()` 钩子已在，未配置）。
5. **一次有界纠正不等于保证**：模型仍可能画错，界面会如实标「图里的 X 和你说的颜色对不上」，不会假装满足。
6. **首页主视觉仍是 ~97KB 的静态图**，没做 AVIF，也没有按网络条件换图。
7. 素材说明里仍标「AI 生成」水印；首页灵感图未授权商用。
8. `pln_101`~`pln_109` 等验收副本可清理（不影响功能）。
